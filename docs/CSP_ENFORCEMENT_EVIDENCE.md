# Content Security Policy (CSP) Strict Script Hash Enforcement

## 1. Threat Model & Challenge

Next.js static export (`output: export`) injects inline `<script>` tags for React Server Components flight payloads (`self.__next_f.push(...)`). Standard configurations often resort to `script-src 'self' 'unsafe-inline'`, which exposes the application to Cross-Site Scripting (XSS) if any untrusted user content were reflected into the DOM.

---

## 2. Hardening Strategy

Modern browsers following the W3C Content Security Policy Level 2 and Level 3 specifications enforce the following behavior:

> _When a CSP directive contains a valid hash or nonce source expression (e.g. `'sha256-...'`), modern user agents ignore `'unsafe-inline'` within that directive._

By calculating the cryptographic SHA-256 hash of every inline `<script>` generated by Next.js during static export and placing them into `firebase.json`:

1. **Modern Browsers**: Only scripts matching an explicit cryptographic hash in the allowlist are permitted to execute. Injected malicious scripts (XSS payloads) are rejected and blocked.
2. **Legacy Browsers**: Gracefully fall back to `'unsafe-inline'`.

---

## 3. Automated Tooling & Production Hashes

The build verification script `scripts/generate-csp-hashes.mjs` automatically inspects all static HTML pages in `out/`, extracts inline scripts, computes their base64 SHA-256 hashes, and synchronizes `firebase.json`.
